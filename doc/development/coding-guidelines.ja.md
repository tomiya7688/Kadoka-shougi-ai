# コーディング規約

この文書は [Coding Guidelines](coding-guidelines.md) の一部を日本語へ移行した正本です。移行済みの節は「継承の共通規約」です。その他の節は英語原文が暫定正本です。文書言語の扱いは[文書言語方針](../architecture/DOCUMENTATION_POLICY.md)を参照してください。英語版からこの日本語正本へ移動できます。

## 継承の共通規約（必須・レビュー基準）

### 禁止：具象クラス起点の連続継承

- **具象クラス A を継承するクラス B を、クラス C がさらに継承してはなりません。** すなわち `具象 A → B → C` を禁止します。中間の B が具象か抽象かは問いません。
- **`抽象 A → 具象 B → C` は、この禁止規則の違反ではありません。** ただし設計と可読性のレビューは必要です。
- この規則単独では `具象 A → B` の一段の継承を一律には禁止しません。ただし、既存の「具象クラスの継承そのものを禁止」する規則など、より厳しいプロジェクト規則を常に優先します。
- `Object`、`System.Object`、`java.lang.Object` など言語に暗黙で存在する最上位の基底型と、インターフェースの継承・実装は、この違反判定の対象外です。

### 継承を選ぶ前の設計原則

- **具体的な処理を持つクラスの継承は原則として避けます。** 抽象クラスでも具体的な実装を持つ場合は同じです。継承関係自体に意味がなく、処理の再利用だけが目的なら、委譲または合成を優先します。
- 基底型と派生型に共通する意味のある形や契約が実際に存在する場合、または同じ形の型が今後必要になると合理的に予想できる場合に限り、継承を検討します。「いつか使うかもしれない」という理由だけで抽象化や継承階層を作りません。
- 形式上許可される継承でも、階層が読みづらい、責務の理解が難しい、変更の影響が過大、置換可能性が成立しないなどの問題があれば、レビューで不合格とします。禁止規則に抵触しないことは、設計の承認を意味しません。

### 適用範囲と例外

- 意図的にその継承構造を採用し、設計の正本に理由と適用範囲を明記している箇所は例外にできます。同じ形の既存コードがあるだけでは、例外の根拠になりません。
- コンパイラや解析器が入力として扱う言語の継承仕様、サンプル、検証用fixtureと、このプロジェクト自身の実装規約を区別します。
- この規約は、新規作成・変更するプロジェクト所有コードに適用します。無関係な既存コードの一斉変更は求めません。
